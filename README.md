# Практична 1 — власний блокчейн

Навчальний блокчейн з рахунками, Ed25519-транзакціями, SHA-256 Proof of Work, власним деревом Меркла та узгодженням незалежних HTTP-вузлів за сумарною роботою. Усі блокчейн-алгоритми реалізовані в цьому проєкті. Криптографічні примітиви, HTTP, процеси й тести надають стандартні модулі Node.js.

## Запуск трьох вузлів

Потрібен Node.js 22 або новіший. Перевірено на 24.22.0. Залежностей npm немає.

```bash
npm start
```

Команда запускає три окремі процеси на `127.0.0.1:4101`, `4102` і `4103`, з'єднує їх і виводить PID та адреси. Ланцюги й мемпули зберігаються у власних каталогах `data/node-4101`, `data/node-4102`, `data/node-4103`. Зупинка через Ctrl+C завершує всі три процеси. Повторний запуск відновлює збережені ланцюги та перевіряє їх. Порти мають бути вільними.

Для окремого процесу доступна команда

```bash
node index.js node --port 4101 --data data/node-4101 --peers http://127.0.0.1:4102,http://127.0.0.1:4103
```

Кожен процес використовує власний каталог. Сусіди задаються під час запуску або через API. Вузли слухають тільки loopback, API керує навчальними гаманцями цього локального вузла.

## Автоматична демонстрація

```bash
npm run demo
```

Скрипт сам запускає три окремі процеси на вільних портах і проходить увесь сценарій. Спочатку перевіряє однакові ланцюги, поширення транзакції й блоку. Потім перезапускає третій процес із його файлом, від'єднує вузли, створює два розгалуження, відновлює зв'язок і перевіряє вибір більшої сумарної роботи. Транзакція програного блоку повертається в мемпул і підтверджується повторно. Наприкінці легкий клієнт перевіряє доказ Меркла, зокрема відхилення підміненої транзакції.

Кожен етап друкує фактичні адреси, PID, хеші, висоти та результати. Дані демонстрації зберігаються в `reports/network-demo.json`, заголовки легкого клієнта — у `reports/light-client.json`. Тимчасові процеси та їхні каталоги прибираються автоматично. Ця демонстрація має власну мережу та може виконуватися паралельно зі звичайним запуском.

## Ручний сценарій через CLI

У другому терміналі створіть гаманці. Приватні ключі записуються у файли з правами 0600, у консоль виводиться публічна інформація.

```bash
node index.js wallet --out data/alice.json
node index.js wallet --out data/bob.json
```

Скопіюйте адреси з результату замість `ALICE_ADDRESS` і `BOB_ADDRESS`. Приклади нижче використовують перший вузол, для іншого додайте `--url http://127.0.0.1:4102`.

```bash
node index.js mine --miner ALICE_ADDRESS
node index.js send --wallet data/alice.json --to BOB_ADDRESS --amount 10 --fee 2
node index.js mempool
node index.js mine --miner BOB_ADDRESS
node index.js balance --address ALICE_ADDRESS
node index.js balance --address BOB_ADDRESS
node index.js chain
node index.js validate
node index.js peer --add http://127.0.0.1:4103
node index.js sync
```

На свіжій мережі після двох цих блоків Alice має 38 одиниць, Bob має 62, включно з другою винагородою та комісією. Суми — цілі найменші одиниці навчальної валюти. Nonce починається з нуля, CLI отримує наступне значення з вузла. Для негативної перевірки його можна задати явно через `--nonce`.

## REST API

Усі відповіді JSON. Відхилення містить `code` і `message`.

| Метод і маршрут | Дія / тіло запиту |
|---|---|
| `POST /wallets` | Створити гаманець у каталозі вузла. Повертає адресу, публічний ключ і шлях локального файлу |
| `POST /send` | Підписати й надіслати від локального гаманця. Поля `sender`, `recipient`, `amount`, `fee`, необов'язковий `nonce` |
| `POST /transactions` | Перевірити та поширити готову підписану транзакцію |
| `POST /mine` | Намайнити блок. Поле `miner` містить адресу одержувача винагороди |
| `POST /blocks` | Прийняти блок від сусіда або синхронізувати розгалуження |
| `GET /chain` | Повний ланцюг, правила консенсусу та обчислена робота |
| `GET /balance/ADDRESS` | Підтверджений баланс, резерв мемпулу та наступний nonce |
| `GET /mempool` | Непідтверджені транзакції |
| `GET /validate` | Повторно перевірити весь ланцюг |
| `GET /status` | PID, висота, tip, робота, складність, сусіди |
| `POST /peers` | Додати сусіда. Поле `url` |
| `PUT /peers` | Замінити список сусідів. Поле `peers`, порожній масив ізолює вузол для демонстрації fork |
| `POST /sync` | Перевірити ланцюги сусідів, обрати більшу роботу, відновити пропущені транзакції |
| `GET /headers` | Заголовки з хешами для легкого клієнта |
| `GET /proof?height=2&index=1` | Транзакція й доказ включення за її індексом у блоці |

## Додаткові завдання

Виконано два завдання з методички.

1. **Доказ Меркла та легкий клієнт.** `src/light-client.js` зберігає заголовки, перевіряє генезис, зв'язки, час, складність і PoW. Транзакцію та її Merkle-шлях отримує окремо. Збережений root використовується для перевірки включення. Повні вузли перевіряють коректність самих переказів і балансів.
2. **Обмеження розміру блоку та відбір за комісією.** Увесь канонічний JSON блоку обмежений 8192 байтами, включно із заголовком, винагородою й хешем. Майнер обирає найбільшу абсолютну комісію серед транзакцій із доступним наступним nonce. Враховуються залежності nonce, межа байтів і зміна кількості цифр mining nonce. Невключені транзакції залишаються в мемпулі. Тести використовують також межу 1024 байти, щоб явно показати пріоритет і відкладення переказів.

Після ручного сценарію на свіжій мережі легкий клієнт запускається так

```bash
node index.js light-sync --file data/light-client.json
node index.js proof --height 2 --index 1
node index.js verify-proof --file data/light-client.json --height 2 --index 1
```

CLI прив'язує перевірку заголовків до генезису та правил цієї мережі. Заголовки не дають легкому клієнту повної історії балансів. Детальна перевірка стану виконується повними вузлами.

## П'ять атак

```bash
npm run attacks
```

| Дія нападника | Очікувана відмова |
|---|---|
| Змінити суму підтвердженої транзакції старого блоку | `MERKLE_MISMATCH` |
| Змінити timestamp старого блоку й заново отримати правильний PoW для нього | `PREVIOUS_HASH_MISMATCH` у наступному блоці |
| Надіслати транзакцію з підробленим підписом | `INVALID_SIGNATURE` |
| Створити два різні перекази, кожен витрачає весь баланс разом із комісією | Другий відхиляється `INSUFFICIENT_FUNDS` через резерв першого |
| Повторно надіслати підтверджений переказ | `NONCE_TOO_LOW` |

Скрипт показує змінені дані та фактичну реакцію перевірки. Результат записується в `reports/attacks.json`. Для другої атаки старий блок перемайнено, тому перевіряється саме розрив зв'язку з наступним блоком.

## Тести

```bash
npm test
```

Набір містить 35 тестів. Охоплено серіалізацію, підписи, чотири правила мемпулу, парне/непарне дерево, PoW, винагороди, баланс, nonce, корекцію складності, п'ять атак, файл стану, дві додаткові можливості та три незалежні HTTP-процеси. Окремий тест показує, що коротший ланцюг може мати більше роботи. Перевіряються також відкат при помилці запису й відновлення пропущених транзакцій після порушення порядку gossip.

## Експеримент зі складністю

Для графіка потрібен Python 3.10+ з Matplotlib. Підготовка середовища виконується один раз.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
npm run experiment
```

Виконуються рівні 1, 2, 3 і 4 шістнадцяткових нулів, по 10 запусків на кожен. Кожна спроба отримує окремий заголовок. Початковий прогрів не входить до вимірів. Для більшої вибірки доступне `npm run experiment -- --runs 30`.

Файли результатів створюються локально.

- `reports/experiment.json` містить усі 40 спостережень, заголовки, nonce, хеші, кількість спроб, wall/CPU time, середні, стандартне відхилення, мінімум, максимум і співвідношення.
- `reports/experiment.csv` містить сирі виміри.
- `reports/mining-difficulty.png` і `.pdf` містять графік середнього часу, спостереженого діапазону min/max та окремих вимірів. Вісь часу логарифмічна.

Кожен додатковий шістнадцятковий нуль зменшує ймовірність успіху одного хешу в 16 разів. Очікувана кількість спроб дорівнює 16 у степені difficulty. Час за сталої продуктивності зростає приблизно так само. Реальні середні на десяти запусках залежать від випадкового розподілу кількості спроб, прогріву та навантаження CPU. Розкид показано на графіку.

Фактичний запуск 13.11.2026 на Node.js v24.22.0, Intel Xeon E5462, по 10 вимірів.

| Складність | Середній час, мс | Вибіркове стандартне відхилення, мс | Діапазон, мс |
|---|---|---|---|
| 1 | 0.407 | 0.491 | 0.036–1.564 |
| 2 | 9.863 | 11.489 | 0.373–31.594 |

| 4 | 1019.505 | 677.964 | 3.457–2025.955 |

Середній час між рівнями 1 і 4 зріс приблизно у 2507 разів. Теоретичне співвідношення очікуваної кількості спроб становить 4096. Відхилення узгоджується з малою вибіркою та значним випадковим розкидом пошуку nonce.


## Правила консенсусу та збереження

Параметри визначено у `src/block.js`. Генезис має фіксовані поля й однаковий PoW на всіх вузлах. Заголовок містить height, timestamp у мілісекундах Unix, previousHash, merkleRoot, difficulty і mining nonce. Хеш заголовка — SHA-256 канонічного JSON. Транзакції підписуються Ed25519 над канонічним JSON усіх полів, крім signature. Адреса — SHA-256 DER/SPKI публічного ключа.

Початкова складність 2, межі 1–5, корекція після кожних чотирьох блоків. Цільовий інтервал 1000 мс. Для вікна з K блоків вимірюються K−1 інтервалів між їхніми timestamp. Старий timestamp генезису не впливає на перше вікно. За часом меншим за половину цільового складність зростає на один нуль, за часом більшим за подвоєний цільовий — зменшується на один. Додавання нуля змінює роботу в 16 разів, тому така спрощена регуляція є грубою.

Робота блоку дорівнює `16 ** difficulty`, сумарна робота обчислюється як BigInt із перевірених заголовків. Передане сусідом числове значення роботи не визначає вибір. За однакової роботи вузол зберігає свій поточний ланцюг. Після реорганізації чинні перекази відкинутих блоків повертаються в мемпул. Перекази, які конфліктують із переможною історією за nonce або балансом, відхиляються з поясненням у результаті синхронізації.

Винагорода 50 одиниць плюс усі комісії стоїть першою транзакцією блоку. Під час перевірки вона зараховується після звичайних переказів, щоб нова винагорода не фінансувала витрати в тому самому блоці. Розміри сум обмежено безпечними цілими JavaScript. Ланцюг і мемпул записуються через тимчасовий файл та атомарний rename. Завантаження повторно перевіряє історію й правила мережі. Помилка запису відновлює попередній стан вузла в пам'яті.

Майнінг працює в worker thread, HTTP-процес обробляє мережу паралельно. Знайдений блок відхиляється як `STALE_WORK`, якщо за час обчислень змінився tip. Синхронізація повторно порівнює роботу перед зміною поточного стану.

Це локальна навчальна мережа з адміністративним API. Її PoW спирається на перевагу чесних обчислень. Учасник із більшою потужністю може створити історію з більшою роботою. Підписи й повна перевірка стану при цьому залишаються обов'язковими.

## Модулі та відповідність методичці

| Вимога | Реалізація та перевірка |
|---|---|
| Гаманець, адреса, підпис | `src/wallet.js`, `src/transaction.js`, тести підпису й полів |
| Детерміновані байти | `src/common.js`, `canonical()` і тест порядку ключів |
| Чотири перевірки мемпулу | `Blockchain.addTransaction()`, тести signature/balance/nonce/duplicate |
| Блок, SHA-256, власний Merkle | `src/block.js`, `src/merkle.js`, парні/непарні тести |
| PoW, винагорода, корекція | `mineBlock()`, `expectedDifficulty()`, тести швидкого/повільного вікна |
| Генезис, баланс, повна перевірка | `src/blockchain.js`, `validateChain()` |
| Збереження й перезапуск | `save()/load()`, atomic write, перезапуск третього процесу в demo |
| Три вузли, обмін, більша робота | `src/node.js`, `scripts/network.js`, `scripts/demo.js`, HTTP-тест |
| Повернення відкинутих транзакцій | `adoptChain()`, demo та тести reorganization |
| Усі команди керування | `src/cli.js`, REST API вище |
| П'ять атак | `scripts/attacks.js`, `reports/attacks.json` після запуску |
| Від 12 тестів | `npm test`, фактично 35 |
| 4 рівні × 10 запусків, графік із розкидом/log axis | `scripts/experiment.js`, `scripts/plot_experiment.py` |
| Три вузли однією командою | `npm start` |
| Два додаткові завдання | LightClient/Merkle proof, byte limit/fee selection |

Матеріали результатів, ключі, стан, залежності й оригінал методички виключені з Git. Для звіту результати потрібно брати з фактичних запусків.

Для використаних стандартних API доступна офіційна документація [Node.js Crypto](https://nodejs.org/docs/latest-v24.x/api/crypto.html) та [Worker threads](https://nodejs.org/docs/latest-v24.x/api/worker_threads.html).
